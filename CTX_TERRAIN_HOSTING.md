# CTX terrain hosting and release publishing

The application keeps the processed CTX collection out of Git and the static site bundle. The current collection is 99 validated tiles, each represented by a JSON sidecar and a binary `.f32` file, plus `catalog.json`. The browser loads the catalog on selection, lazily fetches needed tiles, verifies each binary with SHA-256, and does not treat failed requests as cached terrain.

## Local Rails development

Keep the collection in `data/processed/ctx-jezero/` and run:

```powershell
bundle exec rails server
```

The app uses the same-origin `/ctx-terrain/` route on localhost. That controller reads the ignored processed directory directly; it is not part of the Vercel static deployment.

## Render Rails deployment

`render.yaml` describes one native Ruby web service on the Free plan. It runs `bundle install` and starts Puma with `bundle exec puma -C config/puma.rb`; Puma binds to `0.0.0.0` and honors Render's `PORT`. `/up` is the HTTP health check. The Rails app has no models, migrations, database configuration, sessions, or persistent user data, so it does not need a database or a persistent disk. Rails serves the existing `public/` files directly; there is no asset pipeline or separate precompile step. Render generates `SECRET_KEY_BASE`; no Rails master key is needed because the app does not use encrypted credentials.

Set `CTX_TILE_BASE_URL` in the Render service environment to the exact HTTPS directory URL for a published immutable CTX release, ending in `/`. The Rails layout injects it into the existing page meta tag and the Rails CSP allows only its origin. Leave it unset until a release exists; production does not fall back to the local `/ctx-terrain/` controller. That local controller remains for development only. The Render Blueprint does not set a tile URL or any R2 credentials. Static Vercel remains a separate deployment built from `dist/`, using `CTX_TILE_BASE_URL` during its build; neither deployment includes the processed CTX dataset.

Render Free currently provides 0.1 CPU and 512 MB RAM, spins an idle service down after 15 minutes, and can take about a minute to wake. Its filesystem is ephemeral. This app does not write durable data, and its terrain calculations run in the browser, so it has no server-side raster or database workload; actual memory use still needs observation on the hosted instance. These limits make it suitable for a hobby/demo service but not an always-on production service. The service must be connected to the repository and created from `render.yaml` in the Render dashboard; no deployment has been performed. See [Render Free service limits](https://render.com/docs/free) and [compute plans](https://render.com/docs/compute-plans).

## Build and tile URL configuration

The static output is generated by `tools/build_dist.py` using `tools/dist_manifest.json`. The build stages and validates the app, then atomically replaces only manifest-listed files. The generated manifest explicitly names three entry pages and the public application assets, including all CTX JavaScript modules and their import dependencies. `dist/.generated-manifest.json` records each generated path, size, and SHA-256 and is written last. The manifest separately names `js/mars-globe.js.bak` as an independent existing distribution asset; it is never copied or overwritten. Other unlisted files in `dist/` are also left alone. The build never copies the large CTX collection into `dist/`.

Set `CTX_TILE_BASE_URL` in the Vercel Production environment to the HTTPS directory for a published immutable CTX release, ending in `/`, for example:

```text
https://terrain.example.org/ctx-jezero/releases/4c71dcb9a6bb652bbca9/
```

The static build injects this into the existing `ctx-tile-base-url` meta element. `vercel.mjs` reads the same variable and adds only its URL origin to `connect-src`. Set the variable in Preview as well if preview deployments should use hosted CTX data. When unset, the build leaves the URL empty, the CSP does not allow a tile host, and the planner reports CTX hosting as unconfigured. Use a full HTTPS URL with no credentials, query, or fragment.

The browser uses the local Rails `/ctx-terrain/` endpoint only when the page host is `localhost`, `127.0.0.1`, or `::1` and no production base URL is configured. Production has no Rails CTX controller on Vercel and never falls back to that local route.

The intended Vercel build is `npm run build` with Node.js and Python available; its output directory is `dist/`. Configuration logic currently lives in `vercel.mjs`, but the current working tree has no `vercel.json`. Vercel's documented project configuration files are `vercel.ts`, `vercel.toml`, and `vercel.json`; therefore the deployment settings in `vercel.mjs` are not verified as applied by Vercel unless equivalent project dashboard settings are present. That pre-existing configuration gap was not changed as part of Render preparation.

## Build a verified release plan

`tools/publish_ctx_tiles.py` checks the official dataset identifier, catalog version, full-coverage flag, non-partial selection, all 99 tile identities, sidecar identity/version/source hash, exact file names and sizes, and every `.f32` SHA-256 before it plans any remote operation. It publishes only `catalog.json`, the 99 catalog-listed sidecars, and the 99 catalog-listed binaries. It does not upload the source GeoTIFF or unrelated directory contents.

The release directory is fingerprinted from all published relative paths and checksums. A content change creates a new release prefix; objects under an existing prefix are treated as immutable. Before the first write, the tool checks every remote key for a matching SHA-256 and size or a definite not-found response. A collision or access error prevents all uploads. It uploads sidecars and binaries first, then writes `catalog.json` as the final release commit/discovery object. If any payload upload fails, it withholds the catalog so the incomplete release is not advertised. It never calls a remote delete operation. It reports planned/uploaded/skipped/failed assets and exits nonzero when failures remain.

PowerShell dry-run (the default mode also dry-runs):

```powershell
$env:CTX_TILE_DESTINATION = "s3://your-bucket/ctx-jezero"
$env:CTX_TILE_PUBLIC_BASE_URL = "https://terrain.example.org"
python tools/publish_ctx_tiles.py --dry-run
```

The plan prints a `release_id` and remote base key. Before a real publish, configure the S3-compatible endpoint and credentials in the shell or secret manager. For R2, use the account's S3 endpoint and `AWS_DEFAULT_REGION=auto`:

```powershell
$env:CTX_TILE_ENDPOINT_URL = "https://ACCOUNT_ID.r2.cloudflarestorage.com"
$env:AWS_ACCESS_KEY_ID = "<access-key-id>"
$env:AWS_SECRET_ACCESS_KEY = "<secret-access-key>"
$env:AWS_DEFAULT_REGION = "auto"
python tools/publish_ctx_tiles.py --publish
```

The uploader requires the AWS CLI to be installed separately; this project does not add a Python or JavaScript cloud SDK. The command above is documented only. No credentials or destination have been configured here, and no external upload has been performed. The actual publish report includes the final public base URL if `CTX_TILE_PUBLIC_BASE_URL` is set; copy that exact release URL, with trailing `/`, into Vercel's `CTX_TILE_BASE_URL` and redeploy.

## Object response and browser policy

Configure public read access for the release objects while keeping upload credentials private. A restrictive CORS policy should allow the deployed application origins and only these read methods:

```json
[
  {
    "AllowedOrigins": ["https://your-production-domain.example"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": [],
    "ExposeHeaders": ["Content-Length", "ETag"],
    "MaxAgeSeconds": 86400
  }
]
```

Add an exact Preview origin only if it needs terrain access. The browser currently uses GET; HEAD is useful for operator checks. Return `application/json` for `catalog.json` and sidecars, and `application/octet-stream` for `.f32`. Serve everything over HTTPS. The uploader sets `Cache-Control: public, max-age=31536000, immutable`; because each dataset revision has a new fingerprinted release URL, the cache does not need to revalidate old releases. Do not mutate objects at an existing release URL.

The application CSP `connect-src` is generated from the origin of `CTX_TILE_BASE_URL`, alongside the existing NASA WMTS/ArcGIS endpoints. CORS must separately allow the application page's exact origin. Publish each changed dataset under a new fingerprinted release path and update Vercel's `CTX_TILE_BASE_URL` in the same deployment. Keep prior release objects available for the period that deployed pages and caches may still reference them; do not mutate or delete objects at an existing immutable path. A missing object should return an ordinary 404/non-2xx response. The tile manager surfaces a load error and does not cache that failed tile as valid terrain; fix the host path or republish a complete release instead of serving placeholder elevation bytes.

## Verify a public release

After publishing and configuring the public read origin, run the read-only verifier with the exact release URL and deployed application origin. The representative check fetches and validates the catalog, five sidecars and one-byte binary range responses chosen across the 11-by-9 grid, response CORS, and an OPTIONS preflight:

```powershell
python tools/verify_ctx_release.py --base-url $env:CTX_TILE_BASE_URL --app-origin "https://<deployed-app-host>"
```

For a complete check that streams all 99 binaries and verifies every byte count and SHA-256 against its sidecar, add `--full`:

```powershell
python tools/verify_ctx_release.py --base-url $env:CTX_TILE_BASE_URL --app-origin "https://<deployed-app-host>" --full --timeout 60
```

The verifier performs only public HTTPS GET (including a one-byte `Range` request for representative binaries) and OPTIONS requests. It needs no AWS credentials and does not change remote objects. It expects HTTP 200 for JSON and full binary responses, HTTP 200 or 206 for a range response, `application/json` for `catalog.json` and sidecars, `application/octet-stream` for `.f32`, and `Access-Control-Allow-Origin` matching the supplied application origin (or `*`) on GET responses. The preflight should return 200 or 204, echo/allow the application origin, and advertise GET and HEAD. Any `FAIL` line identifies the failing asset or check; common causes are an incomplete catalog/release, a missing or stale sidecar/binary, incorrect object metadata, a CORS policy/cache that has not refreshed, or a base URL that points at the wrong release prefix. A nonzero exit means the release is not verified. A passing representative check validates headers and reachability for only the selected five binaries; use `--full` to establish complete size/hash integrity across all 99. Neither mode substitutes for loading CTX in a browser against the deployed app.

For local development, start Rails and use the local endpoint; it does not require a production host. For static Vercel production, configure `CTX_TILE_BASE_URL`, publish the immutable release to public HTTPS object storage, and apply the public CORS policy. The Rails controller is not part of Vercel's static deployment.
